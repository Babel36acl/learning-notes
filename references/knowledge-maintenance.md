# 知识库长期维护

采集允许宽松；正式加工根据再次阅读、查找、比较和引用的需要选择深度。不要求每段材料形成文章，也不要求所有问题最终变成一个确定的判断。

## 归属与关系

沿用既有目录保存对象记录、通用解释、项目采用、摘录和历史。项目案例可进入概念页帮助理解，细节也可留在项目页；不要机械删除数字、单位或项目语境。

相同问题的主要解释尽量集中，具体案例、相反观点和不同来源可以并列、互引。不要把“有一处主解释”扩大为只能保留一种说法。日常速查允许必要重复，修改时保持其数字和条件一致。

MOC 可以承担入口、阅读线索或临时汇集材料的作用。分组和关系说明按需要增加，不限制为纯目录，也不要求每个目录生成一篇导论。历史记录保留当时语境，不因旧 ID 或相同关键词被认定为应删除的重复。

## 取舍与融合

比较段落和信息点：同义重述可以去重，新条件、新例子、反例、修正及不同情境的观察都可能有价值。优先在相关解释处补充，不一律追加到文末。若新的材料改变理解，保留有解释意义的旧想法及修正原因，不伪装成从一开始就知道。

抽取可复用模式时去掉不必要的机密和身份细节，保留改变含义的架构、设备、周期、版本和量纲。不能只删内部变量和项目名便宣称已经通用。不能仅凭长度、日期、AI 文风或长期未打开就删除内容。

已有长章先按标题定位。独立查阅、引用或更新的需要出现后再拆；不能用原子化要求切断推导。摘录和原记录仍可保留，不因生成摘要就批量替换原文。

## 操作留在正文之外

在授权范围内保存原件、检查相关引用，检测并发变化。未受影响主题不重构，不建立固定的治理报告或每轮任务闭环。必要的保存回执与检查结果留在对话；知识正文不记录 Agent 的盘点、覆盖率或未来写作计划。

## 正式维护的范围与出口

正式融合时确认问题与资料范围，读取相关来源和已有解释，比较增量与条件，再决定改什么并核对保存结果。按实际需要展开，不把这一骨架用于一句速记。直接使用已有页、只补一句条件、保留未解问题、无需修改都是正常结果；读取失败应另行说明。

需要可追溯的多源维护时，在任务记录中保留实际使用的来源位置、读取范围和版本。高风险或批量任务可用文件哈希固定快照；普通想法不因此要求哈希。来源在阅读后改变时，重读影响本次主张的部分。人读引用与工具维护的来源清单应对应，引用实际使用的子集即可；没有校验工具时不假装标记具备自动保护能力。

冲突先比较对象、版本、时间、单位和前提，方法见 [按问题检索与核验](knowledge-inquiry.md)。修正主要解释后，只检查真正依赖它的摘要、案例和入口；反链用于寻找候选，不是批量替换清单。

## 讨论与输出回流

用户明确要留下讨论收获时，抽出新增的条件、例子、反例或修正，补回解释所在处。保留来源与必要语境；不把整段聊天、多个最新版总结堆到文末。没有新增信息时提供已有入口即可。

原始资料、用户批注、整理页、对外输出可以互相追溯，沿用现有目录，不另造固定 raw/wiki/output 树。AI 摘要或文章中的二次表述不能变成另一份独立证据；需要核实时回到它所依据的材料。AI 生成页经过人工修改后，人工增量也必须保留，不能整页当成缓存重建。

收件箱可以留待以后处理，不以清零为目标。当前问题已获得足够依据且继续加工没有必要增量时即可停下；用户明确要求全量盘点或完整阅读时，先覆盖约定范围，再结束。长期探索不自动设置截止日期，回顾按 [按需回顾](review-on-demand.md) 处理。
